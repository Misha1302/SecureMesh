# Repository Guidelines

## Как ориентироваться в проекте

Сквозной сценарий SecureMesh — отправить зашифрованный текст, пережить обрыв связи и доставить сообщение из локальной очереди. Интерфейс и транспорт находятся в `apps/client_flutter/lib/`, MLS и очередь SQLCipher — в `src/crypto_core/`, HTTP/WebSocket API и миграции PostgreSQL — в `src/SecureMesh.Api/`. Формат сетевых кадров задан в `contracts/runtime/wire.proto`. При изменении контракта проверяйте отправителя и получателя. Границы работ и порядок чтения ТЗ описаны в [AGENTS.md](AGENTS.md).

## Локальная разработка

Запускайте команды из корня репозитория. Для второго рабочего дерева заранее выделите отдельные порты и проект Docker Compose по примеру в [README](README.md).

| Команда | Назначение |
|---|---|
| `make bootstrap` | Запускает PostgreSQL и Mailpit, готовит зависимости и локальный TLS-сертификат. |
| `make demo` | Запускает HTTPS API в текущем терминале. |
| `make smoke` | Проверяет доступность API и доставку сообщений. Запускайте во втором терминале. |
| `make verify` | Запускает сборки, тесты и проверку критериев приёмки. Причины сбоев ищите в `reports/evidence/`. |
| `make down` | Останавливает локальный стенд, сохраняя том базы. |

## Стиль кода и тесты

Для Dart используйте отступ в два пробела и `dart format`, для Rust — четыре пробела и `cargo fmt --manifest-path src/crypto_core/Cargo.toml`. Имена Flutter-тестов заканчивайте на `_test.dart`. Из `apps/client_flutter/` запускайте `flutter analyze --no-pub` и `flutter test --no-pub test`.

Для изменений криптографии начните с `make crypto`. Серверные интеграционные сценарии находятся в `tests/integration/`. Если меняете доставку, прогоните `make native-network-gprs` и `make native-network-severe`. Проверьте задержку, пропуски и дубли. В рабочей матрице под `reports/` укажите команду, платформу, код выхода и ссылку на результат.

## Коммиты и pull request

Описывайте одно связное изменение в коммите. В истории приняты короткие заголовки с глаголом, например `Restore the frozen brief checksum`. В PR укажите затронутый сценарий, способ проверки и оставшиеся ограничения. Для изменения интерфейса приложите снимок с синтетическими данными. Храните тестовые пароли и ключи вне Git. Статус выпуска ведите отдельно от результатов локальных тестов.
