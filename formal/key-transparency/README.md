# Ограниченная модель допуска отправки и подтверждения каталога

Дата проверки 28 ноября 2026 г. Модели описывают требования к реализации. Соответствие Rust, серверов и транспортов переходам модели требует отдельной проверки.

## Допуск одного сообщения

В `SendGate.tla` один отправитель, один чат, один логический идентификатор сообщения и два возможных устройства получателя. Изначально лист 0 авторизован. Единственный следующий снимок отзывает лист 0 и авторизует лист 1. Снимок может появиться во время офлайна, до подготовки, между подготовкой и передачей либо после передачи до ACK. `Dispatch` фиксирует передачу байтов транспорту. Запись наблюдателя сравнивает лист именно в момент передачи с последним когда-либо принятым состоянием. Пакет, переданный до принятия отзыва, может дойти позднее.

Инварианты проверяют допуск, отсутствие молчаливого отката и снятие сообщения с очереди только после доставки. Потеря ACK разрешает повтор того же логического сообщения. Доставка хранится одним битом для этого идентификатора. Дедупликация нескольких сообщений, точный счёт копий, несколько чатов и произвольное число эпох в перебор не входят.

Обычный перезапуск представлен сохранением атомарно записанного состояния. Восстановление копии принимается как обнаруженное либо безусловно отправленное в карантин. Оно возвращает старую эпоху и старую заготовку конверта. Выход из карантина требует свежей сверки и безопасного вступления. `highWater` хранит историю для проверки свойства и недоступен алгоритму допуска. Если платформа может молча принять незамеченный откат, эта модель не устанавливает безопасность платформы.

Проверка подписи и авторизации, полное доказательство истории, корректный источник свежести, безопасный MLS-переход и сериализация передачи с принятием снимка — предпосылки. Проверенная свежая синхронизация видит текущую вершину. Истечение срока моделируется отдельным переходом. Недостоверные или старые ответы не могут продлить срок. Контрольно-точные интервалы, часы ОС, получение имени и ключи человека требуют собственных проверок.

Для прогресса предполагается, что наступает период устойчивой доступности транспорта и кворума, с достаточной свежестью, без новых восстановлений и потерь ACK. Постоянно доступные операции синхронизации, вступления, подготовки, передачи, доставки и подтверждения исполняются по слабой справедливости. При этих условиях TLC проверяет, что сообщение в итоге покидает очередь.

## Кворум

В `Witnesses.tla` четыре фиксированных участника, один из них может подписывать обе несовместимые вершины одного размера с общим родителем. Честный участник записывает выбор до подписи. После рестарта этот выбор сохраняется. Подписи привязаны к участнику и вершине. Отдельными шагами выбираются порядок обращений, запись решения, выдача подписи и принятие при трёх разных подписях. TLC проверяет, что две конфликтующие вершины не могут быть обе приняты. В конфигурации доступности все три честных участника получают одну допустимую вершину, а четвёртый может молчать. При слабой справедливости честных действий вершина в итоге принимается.

Две модели проверяются отдельно. Связь между кворумом и отправкой представлена допущением о корректном результате Sync. Проверки дерева, хранилища свидетеля, конфигурации ключей и реальной сетевой композиции остаются за этой границей.

## Воспроизведение

Использована официальная сборка TLC2 2.19 от 8 августа 2024 г., ревизия 5a47802, из [релиза TLA+ Tools v1.7.4](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4). Наблюдавшийся SHA-256 файла tla2tools.jar — `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`. Linux amd64, OpenJDK 25.0.4.1, один worker, Java heap 256 МиБ.

Из каталога модели выполнить для каждой строки таблицы, задав путь к JAR в TLA_JAR и имена в CFG и MODULE.

```bash
java -Xmx256m -XX:+UseParallelGC -cp "$TLA_JAR" tlc2.TLC \
  -workers 1 -fp 1 -metadir "$(mktemp -d)" -config "$CFG.cfg" "$MODULE"
```
