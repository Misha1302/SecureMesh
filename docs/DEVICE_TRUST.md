# Device trust protocol component

Account login proves verified password and possession of the independent device Ed25519 key. Only the first device becomes trusted at bootstrap; all later devices obtain a bounded pending session. Pending sessions may refresh, log out, inspect their own identity and submit/read their own enrollment request. Private delivery, device administration and conversation creation require trusted status. Existing pre-migration devices retain their original bootstrap status. The migration never converts a pending device to trusted on restart.

An enrollment request contains a versioned domain, stable account UUID, candidate UUID/key, request UUID, random 256-bit nonce and a five-minute issued/expiry interval. Candidate signs the entire request. After comparing the exact candidate transcript by an independent channel, an existing trusted client explicitly approves and signs a distinct domain, its own UUID, full request and candidate proof. Server verifies both signatures and account ownership while holding the account lock and stores the grant; the device remains pending. The new client must verify the old-device pin and grant locally, then sign a domain-separated activation proof. Only this proof activates trust. A revoked approver cannot approve/activate; replay/expiry/concurrent approval fails. Identical local signature retries are durable, and already completed activation is idempotent. Maximum 20 nonrevoked devices per account and 32 enrollment requests per device/day.

The Rust client checks its own candidate identity/key, account, freshness and requested transcript before proof. The approver verifies the candidate signature and refuses to replace an existing pin. Candidate acceptance verifies the old device against an independently confirmed pin, not the directory response. An operator who changes database trust flags cannot manufacture this client certificate. The server can deny service or lie about availability; this protocol does not provide independent key transparency/witnesses or defeat endpoint compromise.

No historical ratchet or traffic secret is copied. Device trust alone does not create MLS membership or reveal old history. The native account hub can exchange request identifiers, compare public keys, approve and verify signed enrollment. Camera QR, MLS leaf insertion across existing chats, revoke/rekey of future epochs, account recovery and history transfer remain required. The process test exercises real signatures/stores and negative cases; full multi-device UI/platform acceptance remains NOT_RUN.

Endpoints: POST /v1/devices/enrollment; POST /v1/devices/enrollment/{id}/proof; GET /v1/devices/enrollment/{id}; POST /v1/devices/enrollment/{id}/approve; POST /v1/devices/enrollment/{id}/activate. Only public certificates/signatures are stored on the server. Enrollment values and bearer tokens must not be logged. Already verified local certificate retries may reuse their cached activation signature after expiry; the server permits late idempotent confirmation only for an activation already committed, never a new expired trust grant.

The sixth migration persists issuance IDs/device IDs/timestamps separately from expired pending requests. Deleting an expired request cannot reset the 32-per-rolling-day limit; idempotent retrieval does not charge another issuance. Account locking serializes the quota check and both inserts. Existing retained requests are backfilled; previously deleted history cannot be reconstructed. This is public metadata, not key/nonce/signature duplication; its retention cleanup policy still needs the broader metadata-retention work. tests/integration/enrollment_quota.py uses real API issuances in an isolated DB, advances only fixture timestamps, checks the limit across restart and the next time window. The same test fails against the earlier binary.

## Сведения об устройствах

Доверенное устройство читает собственный список через `GET /v1/devices`. Сервер возвращает статус доверия и отзыва, `isCurrent` по предъявленной сессии, время первого добавления `createdAt`, время последнего успешного входа с паролем и доказательством владения ключом `lastLoginAt`, а также наличие пригодной для обновления сессии `hasRefreshableSession`. Экран сверяет текущее устройство с ответом `/v1/users/me` и локальным профилем. Время добавления включает устройства, ожидающие подтверждения. Времена refresh, фоновых запросов и сетевого соединения не служат доказательством присутствия человека.

Нативный клиент при входе сообщает семейство своей ОС. Хостнейм и аппаратные серийные номера для этого не требуются. Открывая настройки, пользователь видит своё и другие устройства, а в деталях — источник сведений об ОС, последнее известное время входа и идентификатор. На своём доверенном устройстве можно указать имя или очистить его (`PUT /v1/devices/me/name`). Название и ОС являются пользовательскими и клиентскими сведениями. Проверка ключа и разрешения доверенного устройства по-прежнему используют отдельный протокол.

Миграция `202611270016_DeviceClientMetadata` добавляет необязательные поля. Старые устройства сохраняют ключи и доверие. На старых записях имя, ОС и время входа могут отсутствовать. Вход старым клиентом сохраняет ранее сообщённую ОС. Новая метаинформация доступна только в собственном списке устройств.

В меню устройств «Завершить остальные сессии» отзывает доступ у показанных других устройств с действующими сессиями через тот же API, что индивидуальный отзыв. Подтверждение сообщает о необходимости нового подключения. Текущее устройство исключается. После запросов клиент перечитывает список и отдельно сообщает о частичных результатах. Устройства, подключившиеся после подтверждения, попадут в следующее обновление списка. Каждое изменение требует действующего доверенного устройства; локальные копии истории остаются у получателей.

Показ действующей сессии сам по себе не означает, что человек сейчас в сети.

## Истечение сессии при неактивности

По умолчанию сервер завершает сессию после семи суток неактивности. Вход с паролем и подписанным запросом проверки устройства открывает новое семейство токенов. Для существующих семейств отсчёт семи суток начинается при миграции `202611270018`. Правило действует для обеих версий учётных данных. Сохраняются срок токена доступа 15 минут, срок токена обновления 30 дней с момента выдачи и защита от повторного использования токена обновления.

На доверенном устройстве `GET /v1/auth/session/inactivity` возвращает `idleTimeout` со значением `"1"`, `"3"`, `"7"`, `"14"`, `"30"`, `"90"` или `"never"`, а также `idleExpiresAt` со временем UTC или `null` для `"never"`. Чтобы задать политику для текущего семейства, отправьте `PUT` на тот же адрес, например с телом `{"idleTimeout":"14"}`. Смена политики начинает новый отсчёт. Настройка сохраняется при обновлении токенов. При повторном входе создаётся отдельное семейство с исходной политикой.

Сервер учитывает успешный вход с доказательством владения ключом, явное изменение политики и действие пользователя, о котором доверенный клиент сообщает через `POST /v1/auth/session/activity`. Ответ содержит те же поля, что и запрос политики. Этот запрос предназначен для явного действия, например открытия чата или продолжения сессии после предупреждения. Bearer-токен подтверждает сессию, а физическое присутствие человека сервер установить не может. Обновление токенов, кадры WSS, синхронизация и обычные запросы API срок не продлевают. Источник времени — PostgreSQL, сутки равны 24 часам.

По истечении срока HTTPS и следующий запрос в WSS требуют входа. Токен обновления также отклоняется. Повторный вход использует существующий ключ устройства. Отзыв доверия и изменение состава MLS по-прежнему выполняются отдельными операциями. Серверный срок оставляет локальные ключи, разрешения устройств и состав MLS в силе. Для предупреждения клиент может использовать возвращаемый сервером дедлайн.

Локальная проверка `tests/integration/session_inactivity.py` использует отдельную базу, Mailpit и реальные подписанные входы. Она сдвигает только время последней активности в тестовой базе, сохраняя штатные часы PostgreSQL и API.
