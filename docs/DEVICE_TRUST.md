# Device trust protocol component

Account login proves verified password and possession of the independent device Ed25519 key. Only the first device becomes trusted at bootstrap; all later devices obtain a bounded pending session. Pending sessions may refresh, log out, inspect their own identity and submit/read their own enrollment request. Private delivery, device administration and conversation creation require trusted status. Existing pre-migration devices retain their original bootstrap status. The migration never converts a pending device to trusted on restart.

An enrollment request contains a versioned domain, stable account UUID, candidate UUID/key, request UUID, random 256-bit nonce and a five-minute issued/expiry interval. Candidate signs the entire request. After comparing the exact candidate transcript by an independent channel, an existing trusted client explicitly approves and signs a distinct domain, its own UUID, full request and candidate proof. Server verifies both signatures and account ownership while holding the account lock, then atomically stores the grant and changes trust. A revoked approver cannot approve; replay/expiry/concurrent approval fails. Maximum 20 nonrevoked devices per account.

The Rust client checks its own candidate identity/key, account, freshness and requested transcript before proof. The approver verifies the candidate signature and refuses to replace an existing pin. Candidate acceptance verifies the old device against an independently confirmed pin, not the directory response. An operator who changes database trust flags cannot manufacture this client certificate. The server can deny service or lie about availability; this protocol does not provide independent key transparency/witnesses or defeat endpoint compromise.

No historical ratchet or traffic secret is copied. Device trust alone does not create MLS membership or reveal old history. Actual MLS leaf insertion/ordered Welcome, revoke/rekey of future epochs, camera QR UI, account recovery and history transfer remain required. The test exercises the signed transcript/core with real processes; do not label the whole multi-device feature complete.

Endpoints: POST /v1/devices/enrollment; POST /v1/devices/enrollment/{id}/proof; GET /v1/devices/enrollment/{id}; POST /v1/devices/enrollment/{id}/approve. Only public certificates/signatures are stored on the server. Enrollment values and bearer tokens must not be logged.
