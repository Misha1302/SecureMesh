# Техническое задание. Проверка ключей и разрешение отправки в SecureMesh

28 ноября 2026 г. Статус — требования к разработке. PRODUCTION_APPROVED=false.

## Цель и исходное состояние

Пользователь может начать личный чат по username без обязательной ручной сверки. Для первого сообщения с высокой ценой ошибки доступен режим независимой привязки контакта. На слабой сети клиент сохраняет сообщение в локальной очереди и показывает, когда ожидает подтверждения ключей.

[Исходное предложение](KEY_TRANSPARENCY_RFC_RU.md) сохранено целиком. Настоящее ТЗ уточняет алгоритм и критерии приёмки. В текущем [протоколе установления диалога](MLS_DIRECTORY.md) стороны проверяют pin устройства. Вызовы Rust-ядра `directory_prepare` и `directory_join` привязывают Welcome к запросу и конкретным устройствам. Первоначальный состав чата — два устройства. При переходе к идентичности аккаунта сохранить согласие получателя, одноразовое выделение KeyPackage, проверку подписанного контекста и идемпотентность. Первый вертикальный срез сохраняет состав из двух устройств. Поддержку нескольких устройств принимать отдельным этапом.

## Модель угроз и целевое свойство

Противник управляет каталогом, доставкой и серверными сессиями, может задерживать ответы и возвращать старые корректные доказательства. Предполагаются исправные клиенты, секретность ключей авторизации и заранее известная клиенту конфигурация наблюдателей. Для прототипа с фиксированным составом из четырёх независимых наблюдателей допускается один византийский участник. Потеря связи может остановить отправку. Компрометация конечного устройства, сговор сверх порога и раскрытие сообщения самим адресатом выходят за границы гарантии.

**Инвариант отправки.** В момент передачи приватного конверта транспорту каждое устройство принятой MLS-эпохи принадлежит разрешённому аккаунту, авторизовано в принятой клиентом истории и удовлетворяет политике свежести. Учтён каждый отзыв, уже принятый этим клиентом. Переданные ранее байты могут быть доставлены позднее. Удаление устройства не стирает полученные им сообщения.

Для контакта по имени каталог свидетельствует о согласованности опубликованной привязки. Личность человека при изначально ложной регистрации остаётся неопределённой. В строгом режиме до первой отправки клиент закрепляет AccountId и отпечаток корня через независимый аутентифицированный канал, например личную сверку QR. Ручной статус относится к конкретному корню.

## Обязательные переходы и проверки

1. **Регистрация и полномочия.** Закрытый корень аккаунта хранится у владельца. Для первой версии корень подписывает полный канонический список устройств. Подпись охватывает домен и версию протокола, AccountId, номер версии, хеш предшественника, идентификаторы, ключи, назначения и статусы устройств. Определить однозначное кодирование, начальную версию и правила отказа при дубликатах. Клиент проверяет непрерывную цепочку от закреплённого состояния. Последующие делегирование и пороговое восстановление требуют отдельной спецификации.
2. **Разрешение имени.** Проверить привязки имени к AccountId и AccountId к корню и списку устройств в одной подтверждённой контрольной точке. Переименование сохраняет AccountId. Повторная выдача имени другому AccountId создаёт отдельный контакт. При миграции ранее вручную проверенный ключ устройства должен авторизовать привязку к корню либо пользователь независимо сверяет новый корень. Перевыпуск доступа по почте после потери ключей требует нового закрепления. До этого очередь старого чата заблокирована для новой идентичности.
3. **Контрольная точка.** Проверить идентификатор каталога, версию протокола, эпоху, корень дерева, конфигурацию наблюдателей, кворум подписей за одинаковые данные, доказательства записи и продолжения истории. Каждый наблюдатель проверяет продолжение от собственного состояния и устойчиво фиксирует решение до выдачи подписи, включая параллельные запросы и перезапуск. Для 3 из 4 любые два кворума пересекаются минимум по двум участникам. Для 2 из 3 при одном византийском участнике честное пересечение не гарантировано. Наблюдатели должны иметь раздельные административные ключи и сравнивать подтверждённые состояния. Конфликт зафиксировать и остановить продвижение доверия. Для смены состава требуется проверяемый переход от прежней конфигурации. До его спецификации состав фиксирован.
4. **Свежесть и наблюдение.** До допуска отправки проверять давность подтверждённого состояния, включая первый контакт с пустым кешем. Повторная загрузка старой подписанной точки не обновляет срок. Определить проверяемый источник времени или протокол подтверждения свежести и поведение при откате часов. При неопределённой свежести сохранить черновик. После офлайна проверить всю историю собственной записи с последней точки, в том числе промежуточную замену с последующим возвратом ключа. Пропуск версии требует доказательства, покрывающего интервал. Подтверждение согласованности дерева само по себе не авторизует устройства.
5. **Состав MLS.** На prepare, join через Welcome и входящем Commit до активации эпохи проверить ожидаемый чат, AccountId обеих сторон, полномочия каждого листа, привязку credential и signature key к устройству. Для KeyPackage проверить также срок, ссылку и контекст запроса. Применять политику ко всем поддержанным способам вступления и смены ключа. Запретить неподдержанные переходы. Получение новой записи каталога само по себе не меняет MLS-состав. Новое устройство проходит авторизацию и MLS Add, история прежних эпох ему автоматически не передаётся.
6. **Отзыв и очередь.** Единственная точка допуска в Rust обслуживает обычную отправку, фоновые повторы и восстановление после перезапуска. Сериализовать принятие отзыва и фактическую передачу конверта транспорту. С момента фиксации отзыва приостановить все затронутые чаты до применения Commit, исключающего устройство. Если подготовленный конверт ещё локален, аннулировать его и сформировать новый в допустимой эпохе. Для уже переданного сообщения с потерянным ACK учитывать возможную доставку, сохранять идентификатор логического сообщения и дедупликацию. Повтор в старой эпохе после отзыва запрещён.
7. **Хранилище.** В SQLCipher согласованно фиксировать привязки, контрольную точку, версию списка, состояние MLS, очередь и данные дедупликации. После сбоя повтор допуска проходит через те же проверки. Восстановленную копию считать устаревшей. Если платформа не позволяет надёжно отличить откат, предусмотреть свежую независимую синхронизацию и безопасное повторное вступление до отправки. Повторное использование восстановленного состояния шифрования запрещено.
8. **UX и приватность.** Показывать «Ключ подтверждён каталогом», «Отпечаток сверен вручную», ожидание, конфликт и смену корня раздельно. Критичные запреты действуют также без Flutter. Для приватной индексации использовать механизм выбранной схемы. Оценить перебор имён, видимость запросов оператору и временную корреляцию. Не публиковать открытый перечень пользователей и устройств. Старые клиенты сохраняют независимую сверку или получают отказ в операции, требующей нового протокола.

## Приёмочные сценарии

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Два честных клиента, первый контакт и повтор | Отправка разрешена после проверок, обычный установленный чат в пределах срока свежести не запрашивает свидетелей на каждое сообщение. |
| Ложная начальная регистрация | Автоматический режим показывает уровень доверия каталогу. В строгом режиме несовпадение с независимым отпечатком блокирует отправку. |
| Подмена AccountId, списка, KeyPackage, Welcome или входящего состава | Отказ до применения состояния и передачи сообщения, старый диалог сохраняет прежнюю привязку. |
| Устаревшая подписанная точка на чистом клиенте, неверные часы, откат из копии | До подтверждения свежести и безопасного состояния доступна только локальная очередь. |
| Разные истории, недоступный кворум, перезапуск свидетеля | В пределах модели нет двух принятых конфликтующих точек. Недоступность и доказанный конфликт различимы. |
| Временная замена собственной записи во время офлайна | После подключения виден промежуточный переход даже при совпадении конечного ключа. |
| Отзыв до передачи, до Remove, после подготовки конверта, при повторе и после сбоя | Транспорт не получает конверт со старым составом после принятого отзыва. После исключающего Commit доставка возобновляется, отозванное устройство не читает новую эпоху. |
| Передача до отзыва и потерянный ACK | Возможность прежней доставки учтена. Повтор после отзыва проходит новые проверки, у получателя одна логическая копия. |
| Смена корня, повторная выдача имени, миграция pin | Нет скрытого переноса доверия или перенаправления очереди. |
| GPRS, severe, blackout и восстановление | Для установленного текстового чата сохранить P95 GPRS ≤ 15 с. Отдельно измерить первый контакт, байты доказательств, RTT, расход энергии, задержку отзыва и восстановление очереди. |

До пилота утвердить максимальный возраст точки, окно обнаружения при доступной сети, период проверки собственной истории, условия работы при неопределённом времени, хранение корня, модель восстановления и целевую задержку первого контакта. Численные значения обосновать измерениями и допустимым окном риска. Работа офлайн не даёт клиенту сведений о ещё не полученном отзыве. Отдельно проверить границу между локальной очередью и транспортом на всех путях отправки.

## Текущий native handoff prerequisite (28 ноября 2026)

`securemesh-crypto::api::NativeClient::with_queued_dispatch_snapshot` предоставляет Rust-only точку композиции для будущего KT gate. Под `BEGIN IMMEDIATE` одной SQLCipher базы он заново читает конкретную приватную запись `outgoing` со статусом `queued`, применяет ту же SQL eligibility выборку и sender-ratchet окно, что `outbox(dispatch:true)`, загружает реальную OpenMLS группу, проверяет совпадение текущей эпохи с полем конверта и эпохой декодированного MLS ciphertext, его group ID, тип Application и формат `PrivateMessage`, затем возвращает актуальные device credentials. Сигналы вызова и control-конверты этим API не передаются. Callback получает ту же DB connection до освобождения локальной блокировки. До интеграции typed KT gate он должен оставаться локальным/транзакционным и не выполнять сеть или иные внешние side effects.

Это **не** доказательство Key Transparency и не разрешение на отправку. Будущий callback должен проверить принятый owner-signed roster, свежие подписанные наблюдения и точный набор активных KeyPackage и сравнить roster devices с получателями актуальной OpenMLS группы через ту же connection. Пока потребитель не реализован, API не используется `NativeDelivery`, а обычный Flutter pump продолжает отправлять outbox напрямую. Не считать транспортный инвариант реализованным и не включать защищённый режим в приложении. Callback — доверенный Rust-код, а не API для Dart. Сейчас callback не выполняет сетевых и иных внешних side effects. При ошибке локальная транзакция целиком откатывается; будущая проверка локального clock high-water должна быть отдельным типизированным шагом, сохраняющим только монотонное наблюдение до rejectable handoff staging. После появления реального enqueue его эффект не будет атомарен с локальным COMMIT: нужны стабильный ID конверта и идемпотентность.

Проверки среза: реальные queued MLS сообщения для актуальной эпохи, двухучастниковая группа и отзыв участника с подделкой только внешней эпохи, fail-closed при отсутствующей/сохранённой записи, pending commit, неправильной группе, выходе за sender-ratchet окно или ошибке callback, повторная выдача того же стабильного message ID и сериализация другого локального writer только на время callback. Это не заменяет отзыв/доставку, проверку на Android/iOS/Windows или независимое криптографическое ревью.
