# Безопасность личных сообщений и подключение устройств

Срез исходного кода основной ветки `857208f1f8743342eea6371bd0e63ecbbe841fd5`. Документ описывает доверительные границы при модернизации. Для выпуска нужны отдельные испытания бинарных сборок.

## Границы гарантий

Копия серверной БД раскрывает идентификаторы, принадлежность устройств и служебные данные доставки. При доверенном клиентском бинарнике, сохранённых в тайне ключах устройств и корректной первоначальной проверке собеседника для расшифрования содержимого нужны секреты конечного устройства. Такая предпосылка требует также проверки логов, резервных копий, аналитики и уведомлений. Поиск известного текста в одном дампе служит проверкой утечек, но криптографическую стойкость протокола из этого вывести нельзя.

Активный владелец сервера контролирует поиск, доступность сервиса и ответы каталога. На первом контакте простое нажатие «Совпадают» после просмотра двух значений с одного сервера оставляет связь ключа с человеком непроверенной. Нужны сверка с независимым доверенным каналом, личный QR либо отдельно проверенная система подтверждения каталога. При выборе TOFU доступное свидетельство ограничено непрерывностью ранее замеченного ключа. На этапе внедрения сохраняем независимую сверку. Для автоматической проверки требуется отдельная спецификация соответствия аккаунт → ключ, обнаружения разных представлений журнала и поведения клиента при устаревшем доказательстве.

Доверенный клиент видит открытое сообщение. Компрометация устройства, злонамеренная клиентская сборка или копирование текста адресатом выходят за границы защиты от оператора БД. Удаление устройства ограничивает доступ к новым эпохам после успешного MLS Remove. Старая локальная история может оставаться у получателя. Для интерфейса требуются разные состояния «доступ к сервису отозван» и «ключи всех приватных групп обновлены».

## Контракт клиента для повторной проверки

Локальная операция `peer_key_status(identity, public_key)` возвращает поле `status`. Ответ `unknown` требует первичной сверки, `matches` указывает на совпадение с ранее закреплённым ключом устройства, `changed` блокирует продолжение. Неверная длина или кодировка входного публичного ключа — ошибка операции. Запрос не записывает ключ и не меняет закрепление. Параметр `confirmed` по-прежнему требуется на отдельном шаге записи. При расхождении прежнее значение сохраняется.

Повторный вход в диалог может пройти без ручного подтверждения, когда локальная привязка диалога, собеседника и устройства согласована и закреплённый ключ совпал. Один ответ `matches` не связывает произвольное имя из каталога с этим устройством и не разрешает подключение дополнительного устройства. При отсутствии локальной привязки после миграции безопасный путь — сверка и явное закрепление. Для нового устройства нужны собственные ключ и решение о допуске.

## Условия приёмки

| Приоритет | Владелец | Независимая проверка на тестовых данных | Требуемый результат |
|---|---|---|---|
| P0 | Ядро и Flutter | Первое обращение и повторный запрос, подтверждение, закрытие и повторное открытие БД, сравнение иного значения | Последовательность unknown, unknown, matches, changed; первоначальный ключ по-прежнему matches. Отмена сохраняет неизвестное состояние. |
| P0 | Клиент чата | Повторно открыть тот же диалог; затем вернуть заведомо несовместимую метку устройства из изолированного тестового каталога | Точное совпадение локальной привязки открывается сразу. При расхождении остановлена отправка, видны затронутый диалог и способ сверки. |
| P0 | API устройств и клиент | Выполнить enrollment двумя чистыми экземплярами клиента, повторить при потерянном ACK, истечении запроса и отзыве подтверждающего устройства | Подписи и принадлежность проверены, повтор не размножает устройства. Без отдельного MLS Add/Welcome у нового клиента отсутствует доступ к истории и ключам групп. |
| P0 | Доставка и ядро | На трёх устройствах отозвать одно при офлайн-очереди, обработать Commit во всех затронутых группах, затем доставить новое сообщение | Остальные участники читают текст. Отозванный клиент не расшифровывает новую эпоху. Неотправленные данные обрабатываются по явной политике без отката членства. |
| P0 | Сборки и аудит | Две независимые установки обмениваются уникальными контрольными сообщениями и вложениями. Проверить БД сервера, бэкап, журналы, crash-отчёты и содержимое push | В серверных артефактах отсутствуют открытый приватный контент и клиентские секреты. Зафиксированы доступные метаданные, версии клиентов и границы выборки. |
| P0 | Миграции | Открыть копию старого зашифрованного профиля, последовательно прервать обновление и открыть вновь | История, закрепления и очередь сохраняются. Ввод неверного секрета не заменяет базу пустым профилем. Восстановление проверяется с собственной резервной копией. |

Проверка архитектуры основана на перечисленных исходниках. Для проверки ядра после сборки используется `python3 tests/crypto/process_spike.py`; для API и нескольких устройств предусмотрены `tests/integration/directory.py`, `enrollment.py` и `epochs.py`. Статус целевых межплатформенных и полных продуктовых сценариев фиксируется отдельно.
