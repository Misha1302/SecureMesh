# Техническое задание: SecureMesh

## 0. Принципиальное определение

Продукт — независимая социальная платформа, ориентированная на безопасное общение и качественную доставку **текста при 2G**. Референс: функциональные ожидания Telegram, но без копирования его кода, бренда, дизайна один в один или криптографии. Название SecureMesh — **временное рабочее**, без утверждений о товарном знаке и без включения сторонних логотипов.

### Непереговорные требования

- Личные сообщения и закрытые группы: E2EE на устройствах, сервер не имеет ключей расшифрования, включая администратора.
- Публичные каналы/сообщества: сервер читаемый для поиска и модерации контент; режим чётко помечен в UI.
- Текст в 2G/GPRS/EDGE должен отправляться и приниматьcя через устойчивые механизмы, без гарантий при полном отсутствии сетевого канала.
- Offline-first: отправка в локальную долговременную очередь, чтение кэшированной истории, восстановление синхронизации при возврате сети.
- Никаких самописных криптографических примитивов, обратимо шифруемых паролей или обхода E2EE «для владельца».
- Независимое подтверждение внешним аудитом до публичного production-релиза; пока — статус pre-production.

## 1. Персоны и роли

- Гость: экран входа, публичные страницы с лимитами и учётом приватности.
- Пользователь: регистрируется по username+email+password или passkey (вначале password); номер телефона необязателен; управляет личными чатами, группами, своим профилем и приватностью.
- Автор публичного канала: публикации и медиа, статистика (агрегированная), назначение модераторов.
- Модератор пространства: удаление публичного контента, ограничения в своём пространстве.
- Глобальный модератор: обработка жалоб, блокировки, удаление явно публичного незаконного/запрещённого контента.
- Оператор инфраструктуры: диагностика серверов, метрик и очередей, без доступа к E2EE содержимому.
- Администратор сервиса: управление пользователями, политиками, квотами, ключами сервисов, конфигурацией, аудитом; **не** чтение E2EE сообщений.

Матрица RBAC/ABAC: least privilege; доступ к объектам всегда проверяется сервером, не только UI. Административные опасные операции — MFA, dual approval в production, audit log, reason code.

## 2. Минимально необходимый полноценный набор функций

### Аккаунт и идентичность [FR-A]
- [FR-A01] Регистрация/логин по username, email, паролю; верификация email через локальный Mailpit в dev; официальный SMTP подключается позже.
- [FR-A02] Argon2id с уникальной солью для паролей; password reset меняет только доступ к аккаунту, не восстанавливает ключи E2EE.
- [FR-A03] Access/refresh сессии, отзыв устройства, ограничение сессий, смена пароля, MFA для админов.
- [FR-A04] Профиль, аватар, display name, username, биография, настройки приватности и обнаружения по идентификаторам.
- [FR-A05] Контакты через username; импорт адресной книги только по явному согласию (можно считать расширением).
- [FR-A06] Подключение нового устройства требует подтверждения существующим устройством или защищённого recovery; иначе старая E2EE история недоступна.
- [FR-A07] Удаление аккаунта, экспорт собственных данных с учётом E2EE и жизненного цикла сообщений у других участников.

### Сообщения [FR-M]
- [FR-M01] 1:1 приватные переписки с E2EE и обязательной проверкой членства/состояния ключей.
- [FR-M02] Закрытые групповые E2EE чаты: создание, приглашения, выход, исключение, роли, история, изменения ключей при смене состава.
- [FR-M03] Текст/Unicode, emoji, ответы, редактирование, удаление (запрос на удаление у участников; нельзя обещать удаление чужих копий), реакции.
- [FR-M04] Локальные поиски по расшифрованной истории; глобальный поиск только по публичным данным.
- [FR-M05] Индикаторы «ожидает», «сохранено на сервере», «доставлено устройству», «прочитано (если включено)»; незаметная подмена статуса запрещена.
- [FR-M06] Typing/presence — best effort, не должны задерживать сообщения и выключаются на 2G.
- [FR-M07] Дедупликация по client_message_id в рамках отправителя/устройства/чата, устойчивость к обрывам, повторное получение без потерь.
- [FR-M08] Несколько устройств на аккаунт; отдельные device cursors и хранение состояний MLS на каждом устройстве.
- [FR-M09] Жалобы: добровольное раскрытие выбранных сообщений пользователем модерации, без принудительной «админской расшифровки».
- [FR-M10] Личные чаты без номера телефона, с блокировками пользователей и антиспамом.

### Сообщества и социальная сеть [FR-S]
- [FR-S01] Публичные/ограниченные каналы, посты, подписки, обсуждения, реакции, поиск публичных каналов/постов.
- [FR-S02] Открытые группы и сообщества, роли владельца/модератора, жалобы, бан/мьют, лимиты.
- [FR-S03] Публичная лента подписок (по хронологии в первой версии), счётчики просмотров без индивидуального трекинга по умолчанию.
- [FR-S04] Чёткие UI-маркеры для публичного и E2EE, никакой ложно заявленной приватности.
- [FR-S05] Рассылки в публичных каналах не осуществляются N индивидуальными E2EE сообщениями: хранить один пост + fanout указателей.

### Медиа [FR-F]
- [FR-F01] Фото, превью, графические форматы с разумной фильтрацией; EXIF/геоданные удаляются из публикуемых превью, если согласие не дано.
- [FR-F02] Документы, изображения, GIF/анимации, аудио, видео.
- [FR-F03] Голосовые сообщения (Opus или обоснованный кодек); пауза, перемотка, прогресс, запись с разрешениями.
- [FR-F04] Круглые видеосообщения («кружочки»): захват камеры, локальное сжатие, круглая маска отображения.
- [FR-F05] Возобновляемые чанковые загрузки/скачивания, контроль размера/MIME/контрольной суммы, квоты, отмена.
- [FR-F06] E2EE вложений на клиенте со случайным per-file ключом, AEAD; ключ в MLS-сообщении, сервер хранит только шифротекст.
- [FR-F07] На 2G: по умолчанию только метаданные вложения, никакого автопроигрывания/скачивания медиа; при улучшении сети дозагрузка.
- [FR-F08] Публичные медиа допускают серверное перекодирование, сканирование и CDN. Приватные — нет без локальной обработки и явного действия пользователя.

### Звонки [FR-C]
- [FR-C01] 1:1 голосовые звонки и видеозвонки через WebRTC, сигналинг в сервисе; mute, camera switch, reconnect, hang up.
- [FR-C02] Для продакшена обязателен TURN; в dev может работать локальный coturn, если доступно.
- [FR-C03] Не обещать звонки на 2G; при недостаточной сети показать статус/предложить голосовое сообщение.
- [FR-C04] WebRTC DTLS-SRTP защищает media transport, но это не равно проверенной E2EE против серверного SFU. Групповые звонки/SFU с настоящим E2EE — отдельный релиз и отдельные security gates.

### Интерфейс [FR-U]
- [FR-U01] Flutter приложение для Android и Linux desktop, далее iOS, Windows/macOS; web с чёткой проверкой поддержки E2EE.
- [FR-U02] Чаты, диалог, запись голоса, список медиа, профиль, настройки, каналы, создание пространства, админ-интерфейс.
- [FR-U03] Адаптивный Material 3 + оригинальная дизайн-система, клавиатурная навигация desktop, accessibility, локализация RU + EN.
- [FR-U04] Мгновенное optimistic отображение отправленного сообщения с прозрачным статусом очереди, ошибки с понятным повтором.
- [FR-U05] Lite/2G режим автоматически включается по измерениям канала/повторным таймаутам, можно переключить вручную.
- [FR-U06] Экономия памяти/батареи, виртуализированные списки, ограничение кэша и background polling.
- [FR-U07] Тёмная и светлая темы; никакой обязательной авторизации для локальной публичной демо-ленты (если это безопасно).

### Администрирование и SRE [FR-O]
- [FR-O01] Панель модерации с RBAC/MFA, жалобами, reason codes, журналами действий.
- [FR-O02] Метрики соединений, p50/p95 задержки ACK и сквозной доставки, offline queue size, reconnect rate, media errors.
- [FR-O03] Health/readiness, structured logs с редактированием секретов, tracing без plaintext приватных сообщений.
- [FR-O04] Лимиты регистрации, запросов, отправки, файлов, приглашений; антиспам с минимизацией данных.
- [FR-O05] Резервные копии, проверяемое восстановление, миграции БД, требования хранения и удаления по политике.

## 3. Поведение при слабой сети

В режиме 2G работоспособность **текстовой** отправки и получения обязательна. Передача больших файлов не является требованием для 2G. Проектирование — от трёх факторов: высокий RTT, низкая пропускная способность, обрывы. Все релевантные P0 тесты смотреть в `03_2G_RELIABILITY_RU.md` и `07_TESTING_ACCEPTANCE_RU.md`.

## 4. Не-функциональные требования [NFR]

- [NFR-1] Конфиденциальность: сервер не обладает ключами для чтения личных чатов; минимизировать метаданные, явно описать неизбежные утечки.
- [NFR-2] Целостность: отсутствие логических дублей и потери после подтверждения durable ACK в рамках заданной отказоустойчивости БД.
- [NFR-3] Наблюдаемость: метрики SLI, трассировки, проверяемый аудит, без содержимого секретных сообщений.
- [NFR-4] Повторяемость: локальный bootstrap из чистой среды документирован, Testcontainers/Docker Compose, миграции без ручного SQL.
- [NFR-5] Тестируемость: интеграционные тесты двух устройств (реальный crypto core), хаос-сети, E2E пользовательские сценарии.
- [NFR-6] Изоляция: безопасные конфигурации по умолчанию, TLS на публичных соединениях, RBAC, CSRF для cookie-сессий, CORS allowlist, защитные HTTP-заголовки.
- [NFR-7] Доступность: RU/EN, читаемый контраст, screen readers, масштабы шрифтов, доступная навигация.
- [NFR-8] Эксплуатация: приложение не предполагает открытого постоянного порта и может использовать один внешний TLS-порт 443.
- [NFR-9] Privacy/Compliance: данные минимальны, политики хранения и удаления задокументированы; юридическая оценка перед запуском по регионам эксплуатации.
- [NFR-10] Supply chain: lock-файлы, SBOM, скан зависимостей и контейнеров, pin образов/версий, независимый криптоаудит до production.

## 5. Что не нужно делать «ради галочки»

- Не создавать свой криптоалгоритм, самодельный key exchange, «суперадмина» с чтением закрытых чатов.
- Не делать десятки микросервисов до измерений.
- Не объявлять работу на 2G доказанной по LTE с отключёнными картинками; нужны воспроизводимые netem тесты и реальные EDGE/GPRS испытания перед коммерческими обещаниями.
- Не обещать невозможность взлома, полную анонимность, доставку при полном отсутствии связи или удаление прочитанного на чужом устройстве.
- Не имитировать готовность заполнителями, моковыми сообщениями, фиктивными тестами.

## 6. Definition of Done

Для **полного локального проекта**: P0 по тестовой матрице зелёные, поддержанные клиентские сборки собраны, живые E2E тесты прошли, сценарии медиа/публичных пространств и звонков документированы/проверены, `make demo` запускает стек, `make verify` даёт конечный отчёт, подготовлен deployment handoff.

Для **публичного production** дополнительно требуются независимый аудит, юридическое/операционное ревью, домен/сертификаты, FCM/APNs и SMTP ключи, нагрузочные испытания реальной инфраструктуры, бэкапы с восстановлением, эксплуатационная поддержка, решение владельца. Это НЕ требуется и НЕ разрешено сейчас.
