# Проверка доказательств Meta AKD

Изолированный прототип публикует запись, получает два снимка каталога и передаёт доказательства отдельному процессу проверки. Клиент принимает VRF-ключ и исходную контрольную точку от вызывающей стороны. Для перехода он получает отдельно подтверждённый корень следующей эпохи, проверяет точный интервал и append-only proof, затем заменяет локальную точку. Неудачная проверка сохраняет предыдущую точку. Повторные чтения проверяются относительно уже принятого корня.

Использована версия `akd = 0.13.0` с `WhatsAppV1Configuration` и upstream Protobuf (`LookupProof`, `AppendOnlyProof`). Включены Cargo features `whatsapp_v1` и `public_auditing`; экспериментальная конфигурация выключена. Cargo.lock фиксирует зависимости. Пакет соответствует коммиту [43a60cc](https://github.com/meta/akd/tree/43a60ccf7dfdd8f4b628186410e871192adaf65b). Upstream разрешает MIT или Apache-2.0. NCC Group проверяла v0.9.0 в августе 2023 года; по данным upstream исправления вошли в v0.11.0. Область того аудита не распространяется на этот прототип или все последующие изменения v0.13.0. [Отчёт NCC Group](https://research.nccgroup.com/2023/11/14/public-report-whatsapp-auditable-key-directory-akd-implementation-review/) · [Описание AKD](https://github.com/meta/akd#audit)

## Локальная проверка

Выполнять из этого каталога. Пример использует публичный **тестовый** VRF-ключ из upstream, синтетические значения и непостоянную базу данных. В команде проверки зафиксированы отдельно воспроизводимые значения для этой конкретной фикстуры. Ни одна команда не запускает сетевой сервис. Для первого получения зависимостей Cargo нужен доступ к реестру.

```bash
cargo +1.100.0 test --locked -j2
proof_dir="$(mktemp -d)/proofs"
cargo +1.100.0 run --locked --offline -j2 --example directory -- publish "$proof_dir"
cargo +1.100.0 run --locked --offline -j2 --example directory -- verify "$proof_dir" \
  f6ec49c8085f4d4be69db8e248bf11ce288026f5b8c5f6599defe58303d0702d \
  74a43cd12cdb2d71b90952ff7304d42ca6c0b4e3054104bf90abee23d443638a \
  a22850375f46699f51212791cf8f7e3ddb868eafdebd33aadc5c714960cb52e7
```

Проверено на Linux x86_64, Rust 1.100.0. Получены версии записи 1 и 2. Размеры файлов для каталога с одной меткой и двумя последовательными 32-байтовыми значениями составили 877 и 953 байта для чтений и 230 байт для перехода. Это размеры protobuf без подписей свидетелей и транспортных накладных расходов. Верхняя граница входного файла в CLI и проверяемого ответа в библиотеке — 256 КиБ. Измерение на одной записи не определяет стоимость работы на 2G и при большом каталоге.

Интеграционный тест проверяет также две отдельные метки имени и аккаунта в одной текущей точке. Проверки отказа используют другой запрошенный ключ, другой VRF-ключ, изменённое значение, усечённый ответ, старое доказательство, неверный корень, неверный интервал, пропущенную и ранее принятую эпоху.

## Граница доверия

`Client::from_pin` требует заранее аутентифицированной пары VRF-ключа и точки. Путь доставки подтверждённых корней должен быть независимым от ответа каталога. Корень, заново полученный от единственного оператора, не устанавливает отсутствие разветвления. Проверка продолжения дерева не устанавливает право устройства отправлять сообщения и не обнаруживает все промежуточные изменения собственной записи без отдельной проверки истории.

Дальнейшая интеграция требует операционного управления серверным хранилищем и закрытым ключом VRF, авторизованного формата записи аккаунта и устройств, свидетелей и кворума, проверки свежести, собственной истории и допуска транспорта. Библиотека записывает принятую клиентскую точку в существующий профиль SQLCipher. Flutter и серверные маршруты её пока не вызывают. Совместимость проверена между двумя локальными процессами на одной зафиксированной версии; совместимость мобильных платформ и независимых реализаций ещё не проверена.

## Состояние при перезапуске

Команды `pin`, `advance` и `read` используют существующий нативный профиль с уже инициализированной идентичностью. В них тот же rusqlite 0.41.1 и SQLCipher 4.20.0, что и в crypto_core. Версия поддерживаемого реестра миграций OpenMLS — 6. Пароль профиля передаётся в stdin. Пример предполагает заранее установленную переменную PROFILE с путём, OWNER с идентификатором этого устройства и независимо проверенные VRF, ROOT1 и ROOT2. Пример читает пароль из заранее подготовленного защищённого источника PROFILE_SECRET_FILE; содержимое не передаётся в аргументах процесса. CLI принимает 16–4096 байт UTF-8 без NUL. Пробелы и переводы строк, включая последний LF, входят в пароль. Источник должен выдавать точные байты пароля.

```bash
directory_store() {
  cargo +1.100.0 run --locked --offline -j2 --example directory -- "$@" < "$PROFILE_SECRET_FILE"
}
directory_store pin "$PROFILE" "$OWNER" "$VRF" 1 "$ROOT1"
directory_store advance "$PROFILE" "$OWNER" "$VRF" 1 "$ROOT1" 2 "$ROOT2" "$proof_dir/advance.pb"
directory_store read "$PROFILE" "$OWNER" "$VRF" 'securemesh-demo/account/alice' "$proof_dir/second.pb"
```

Только явная команда pin создаёт запись. Существующая таблица, другой владелец, неверный пароль или неподдерживаемый профиль приводят к отказу. Обычное открытие не создаёт файлы и не восстанавливает отсутствующий pin. Одна запись описывает один каталог. Допустимая эпоха хранилища ограничена диапазоном неотрицательного SQLite INTEGER.

После проверки доказательства транзакция BEGIN IMMEDIATE сравнивает ожидаемую эпоху и корень с уже записанными. Побеждает один из конкурирующих переходов. Для последнего принятого перехода сохранён также предыдущий корень. Повтор после потери ответа заново проверяет доказательство и возвращает AlreadyCommitted для той же пары точек. Если состояние уже продвинулось дальше, старый вызов отклоняется. Чтение возвращает точку, относительно которой проверена запись. Это позволяет различать снимок чтения и состояние после возможного параллельного обновления.

В тесте профиль создаёт NativeClient из crypto_core. Отдельный процесс завершается после записи до COMMIT. После перезапуска сохраняется прежняя точка. Ещё два процесса представляют различные корректные продолжения одной точки, один получает отказ. Победивший процесс завершается сразу после COMMIT, а повтор из вновь открытого профиля распознаёт принятый переход. Проверены неверные пароль и ключ, отсутствие pin, несовместимые схемы и повторное открытие профиля нативным клиентом.

Копирование старого SQLCipher-файла целиком восстанавливает и старый корень. Этот прототип не имеет внешнего монотонного счётчика или свидетельства последнего состояния. После восстановления копии для отправки требуются отдельные процедуры независимой свежей синхронизации и безопасного вступления. Команда pin сама по себе не устанавливает свежесть.

## Хранилище публикующего каталога

`writer::Writer` создаёт отдельную серверную базу SQLCipher, открывает её после перезапуска и публикует изменения через Meta AKD. Пользовательский профиль служит хранилищем проверяющего клиента. Для каталога оператор предоставляет пароль базы и собственный устойчивый провайдер `VRFKeyStorage`. База закрепляет соответствующий публичный VRF-ключ. Тестовый ключ поставляется только вызывающим тестом. Серверный пароль и закрытый ключ в таблицы не записываются.

Опубликованный crate AKD 0.13.0 включает реализацию в памяти и публичный интерфейс Database. Наш адаптер реализует этот интерфейс. Он хранит записи Azks, узлы и значения с индексами по метке, эпохе и версии. Внутренний дисковый формат 1 использует upstream serde для зафиксированной версии; публичные доказательства остаются в upstream protobuf. [Storage API релиза](https://docs.rs/akd/0.13.0/akd/storage/index.html)

Каждая публикация принимает 16-байтовый идентификатор операции, ожидаемую точку и упорядоченный набор меток со значениями. BEGIN IMMEDIATE охватывает чтение предыдущего состояния, вычисление, запись всех записей AKD, контрольной точки и квитанции. На совпадающий повтор возвращается историческая квитанция, даже если каталог уже продвинулся. Для запроса текущей вершины используется checkpoint(). Тот же идентификатор с изменёнными параметрами и новое изменение относительно устаревшей точки отклоняются. Чтение работает в одном снимке SQL. Инициализация публикует готовый файл без перезаписи существующего. Обычное открытие не создаёт отсутствующий каталог или дерево.

Регрессионные тесты создают временную базу, завершают дочерний процесс до и после внешнего COMMIT, проверяют повтор, конкурирующих издателей, неправильный ключ/пароль и отказ при отсутствии метаданных дерева. После восстановления сохранённые исторические доказательства продолжения и актуальная запись проверяются отдельным клиентом. Тест также получает и проверяет через upstream AKD полную историю метки со всеми тремя промежуточными значениями.

```bash
cargo +1.100.0 test --locked --offline -j2 writer::tests
```

Это локальная библиотека. Транзакция удерживает блокировку записи во время построения дерева; SQL-вызовы синхронны и требуют выделенного рабочего потока при интеграции в асинхронный сервис. Квитанции и история не очищаются. Производительность большого каталога, хранение VRF в KMS, ротация ключей, аутентификация/авторизация сетевой публикации, восстановление из резервной копии с независимой проверкой свежести, репликация и свидетели пока не квалифицированы. При восстановлении всей базы из старой копии её внутренние корни и квитанции также откатываются. Продолжение публикации требует внешней сверки последней принятой точки.

## Свидетели и зафиксированный кворум

Библиотека поддерживает четыре заранее заданных Ed25519-ключа. Оператор клиента получает идентификатор каталога (32 байта), VRF-ключ и четыре упорядоченных ключа по отдельному аутентифицированному каналу. У каждого свидетеля свой ключ и свой файл SQLite с публичными контрольными точками. Секретный ключ не записывается в этот файл.

Для совместимых реализаций отпечаток конфигурации равен SHA-256 от последовательности ASCII `SecureMesh/AKD/3-of-4/config/v1`, нулевого байта, идентификатора каталога, VRF-ключа и четырёх ключей в порядке слотов 0–3. Все шесть полей после нулевого байта имеют длину 32 байта. Сообщение Ed25519 состоит из ASCII `SecureMesh/AKD/3-of-4/transition/v1`, нулевого байта, отпечатка конфигурации, предыдущей эпохи (u64 big-endian), её 32-байтового корня, следующей эпохи и её корня в том же формате. Разрешён переход ровно на одну эпоху. Каждый голос передаёт номер слота и 64 байта подписи. Проверка требует 3 или 4 разных слота из закреплённого набора и строгую проверку каждой переданной подписи.

Перед подписью свидетель проверяет доказательство продолжения AKD и фиксирует корень, родителя и эпоху одной устойчивой транзакцией. Повтор того же перехода сразу после потери ответа позволяет снова получить подпись. Иное продолжение уже подписанного родителя отклоняется. Клиент явно включает кворум вызовом `Store::enroll_witnesses` относительно независимо закреплённой точки. Миграция сохраняет корень, владельца и VRF и переводит таблицу в формат 2. После этого `advance_witnessed` проверяет и подписи, и доказательство AKD; старый клиент формата 1 теряет право изменять эту таблицу. Переход на другую конфигурацию потребует отдельного протокола.

Тесты моделируют двух конкурирующих публикаторов, оба с математически корректным продолжением общего корня, перезапуск после потери ответа, повтор, недостаточный кворум, смену каталога и запись из ранее открытого соединения версии 1. Четыре локальных тестовых ключа используются только как фикстура. Действующих независимых операторов SecureMesh пока нет. Каждый оператор обязан держать единственный актуальный журнал для своего ключа. Возврат старой копии журнала или параллельное использование ключа с двумя журналами нарушает предпосылку. Защита от двух несовместимых кворумов предполагает не более одного такого неисправного оператора. При расколе голосов прогресс может остановиться. Протокол подтверждает согласованность; свежесть, идентичность владельца аккаунта и допуск сетевой отправки проверяются отдельно.

## Привязка публичного MLS KeyPackage к записи устройства (этап C)

API хранит UUID аккаунта в `users.id`, полный UUID устройства в `devices.id` и публичный Ed25519-ключ в `devices.public_key`. Нативный MLS-клиент помещает канонический текст UUID устройства в OpenMLS BasicCredential. Запись ниже связывает эти три поля. Ожидаемые AccountId и DeviceId передаёт вызывающая сторона из своей привязки контакта. Username, отображаемое имя и сокращённый отпечаток не являются идентификаторами этой записи.

Канонический формат v1 использует точную конкатенацию полей в указанном порядке. Входные UUID принимаются только в полном нижнем регистре с дефисами, например `00112233-4455-6677-8899-aabbccddeeff`; нулевой UUID отклоняется. Внутри AKD оба UUID записываются по 16 байт в сетевом порядке RFC, без зависящей от платформы перестановки байтов Guid. Обозначение `NUL` означает один байт 0x00.

| Объект | Последовательность байтов |
| --- | --- |
| AKD label | ASCII `SecureMesh/AKD/device-signing-key/label/v1`, NUL, UUID аккаунта, UUID устройства |
| AKD value | ASCII `SecureMesh/AKD/device-signing-key/value/v1`, NUL, UUID аккаунта, UUID устройства, 32 байта канонического Ed25519-ключа основной подгруппы, отличного от нейтральной точки |

Публикатор может передать результат `DeviceAddress::publication` в существующий `writer.publish`. Производный label, точное совпадение назначения и обоих UUID внутри value, длина и кодировка ключа проверяются при чтении. Команда ниже читает бинарный TLS-сериализованный KeyPackage (до 16 КиБ) и доказательство AKD (до 256 КиБ). Она использует существующий SQLCipher checkpoint и тот же нативный OpenMLS-валидатор, который проверяет пакеты в API: suite, подписанный пакет, полный BasicCredential и signing key листа. Команда выведет эпоху и корень только при успехе.

```sh
cargo +1.100.0 run --locked --manifest-path src/key_directory/Cargo.toml --example directory -- \
  check-device "$PROFILE" "$OWNER" "$VRF" "$ACCOUNT_ID" "$DEVICE_ID" keypackage.tls lookup.pb < "$PROFILE_SECRET_FILE"
```

Проверка подтверждает включение записи и соответствие пакета в конкретной сохранённой точке. Для допуска отправки по ТЗ ещё нужны проверенные привязка имени к AccountId, корень владельца, подписанный полный roster с назначениями и отзывами, его непрерывная история и свежесть checkpoint. Эта команда доступна отдельно от транспорта, не меняет pins и не присваивает контактам статус доверия. Политика независимых свидетелей задаётся при регистрации checkpoint отдельно.

## Подписанный корнем список устройств аккаунта (этап C)

Исходное ТЗ: `docs/KEY_TRANSPARENCY_TZ_RU.md` в PR №4, ревизия `ca5ed54ebe2bf4401325e0fd740aa82a9172e3bb`, пункты 1–3. Издатель использует `Roster::new` и `Roster::publication`; переданный владельцем Ed25519 SigningKey подписывает весь список. Секрет корня не сохраняется в этом компоненте. Контакт сначала независимо аутентифицирует AccountId и публичный ключ владельца и один раз закрепляет их в уже подготовленном клиентском профиле. Повтор того же pin сохраняет историю, другой корень отклоняется.

* Label — ASCII `SecureMesh/AKD/account-device-roster/label/v1`, NUL, 16 байт AccountId.
* Тело подписи — ASCII `SecureMesh/AKD/account-device-roster/signed/v1`, NUL, 16 байт AccountId, версия u64 BE, 32 байта SHA-256 тела предыдущего списка, количество записей u16 BE и записи подряд. Для версии 1 хеш предшественника состоит из нулей. Значение AKD — тело и 64 байта строгой Ed25519-подписи. Хеш версии вычисляется по полному телу без подписи.
* Запись — 16 байт полного DeviceId, назначение u8 (1 — Ed25519 signing key поддерживаемого MLS-набора), состояние u8 (0 — активно, 1 — отозвано), 32 байта публичного ключа. UUID используют сетевой порядок байтов. Устройства отсортированы по UUID; пустые UUID, дубликаты идентификаторов или ключей, неканонические ключи, смешение ключа аккаунта с ключом устройства и неизвестные значения полей отклоняются.
* Не более 20 активных устройств и 64 записей за время жизни этой версии формата, включая отозванные. Каждый следующий список сохраняет прежние идентификаторы и ключи. Отзыв необратим. Чтобы заменить ключ устройства, владелец отзывает старый DeviceId и добавляет новый DeviceId с новым ключом. Пустой активный набор разрешён.
* При проверке обязательно доказательство AKD для конечного подписанного значения на сохранённой точке. Между принятой версией и конечной допускается до 32 подписанных промежуточных списков, строго по порядку. Каждая версия проверяется, в том числе промежуточные отзывы. Для промежуточного файла проверяется история подписей владельца; публикация каждого промежуточного состояния в определённой эпохе потребует отдельных доказательств истории AKD.
* Финальная фиксация в SQLCipher повторно сверяет checkpoint каталога, корень аккаунта и предыдущее состояние. Конкурирующее опережающее изменение требует прочитать актуальное состояние и проверить заново. Сбой до фиксации не меняет список, потеря ответа допускает точный повтор. `saved_roster` возвращает историческое локальное решение; оно может быть устаревшим.

```sh
directory_store pin-account-root "$PROFILE" "$OWNER" "$VRF" "$ACCOUNT_ID" "$INDEPENDENT_ROOT_HEX" < "$PROFILE_SECRET_FILE"
directory_store accept-roster "$PROFILE" "$OWNER" "$VRF" "$ACCOUNT_ID" latest-lookup.pb < "$PROFILE_SECRET_FILE"
# При пропущенных версиях передайте их подписанные значения от старшей известной + 1 до конечной − 1.
directory_store accept-roster "$PROFILE" "$OWNER" "$VRF" "$ACCOUNT_ID" later-lookup.pb version2.bin version3.bin < "$PROFILE_SECRET_FILE"
```

Независимое ревью требуется до интеграции. Этот слой не изменяет UI, пины MLS, очереди и разрешение отправки. Он не определяет выдачу/хранение закрытого корня, ротацию корня, миграцию старого ручного pin, восстановление после утраты корня, привязку username к AccountId, защиту от восстановления старой копии профиля, сроки свежести и инфраструктуру независимых наблюдателей. Приложение должно отдельно установить требуемую политику свидетелей каталога. Публичная запись раскрывает список устройств тому, кто получает её содержимое; полноценный анализ приватности и сетевой протокол выдачи остаются отдельными задачами.

`accept_roster` подтверждает и сохраняет авторизованное состояние, но само по себе не разрешает отправку. Состояние с нулём активных устройств допустимо: отзыв последнего устройства блокирует весь аккаунт. Для любого будущего разрешения отправки отдельный delivery gate обязан запретить пустой active set и подтвердить соответствие **каждого** активного устройства своей записи AKD и валидному MLS KeyPackage. Текущий каталог не подключён к транспортному send gate и не проверяет это покрытие автоматически.

`Store::verify_package_set` — следующий изолированный reader-слой. Вызывающая сторона передаёт ожидаемый локальный checkpoint, свежее lookup-доказательство уже принятого roster и по одному KeyPackage с отдельным AKD lookup-доказательством на каждое активное устройство. Чтение и проверка выполняются внутри одной SQLite `IMMEDIATE` транзакции. Reader требует, чтобы expected checkpoint совпал с закреплённым, roster из каталога побайтно совпал с owner-signed roster в профиле, набор UUID был непустым, точным и без повторов, а каждый ключ устройства совпал с roster. KeyPackage до 16 КиБ проверяется штатным OpenMLS validator по полному BasicCredential и leaf signing key. Результат `VerifiedPackageSet` содержит AccountId, checkpoint, версию roster и только проверенные пакеты.

Этот снимок не утверждает актуальность checkpoint относительно удалённого каталога и не является разрешением на отправку. Свежесть/кворум checkpoint и сериализация проверки с реальной передачей в транспорт остаются обязательной отдельной частью delivery gate.
